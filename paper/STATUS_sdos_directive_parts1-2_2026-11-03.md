## B. Part 2: findings, which side was right, and what I changed
1. **KPM resolution at 170 moments.** The text's 0.4 eV was wrong as a sigma-convention number: a = 10.28 eV gives pi a/M = 0.19 eV; the Jackson kernel is Gaussian-like with FWHM 0.45 eV (so "0.4" was neither). All other cases (C3840 0.45, Morrow 0.11, series 0.045) are sigma = pi a/M, which I verified from their `a`. Text now: "Jackson resolution pi a/M = 0.19 eV, a Gaussian-like kernel of FWHM 0.45 eV"; the gap fill (minimum 1.1e-4 at 0.82 eV, from the saved KPM curve) is unchanged.
2. **Memory ratio.** The JSON values: Kwon peak 0.15, 0.45, 1.23, 3.10 GB; DFTB peak 0.35, 1.81, 5.76 GB and (new, see B10) 13.97 GB at 262 144 atoms. Ratios 2.3, 4.0, 4.7 and 4.5 (3.2 with PCG alone). The old "2.3-3.5" was wrong (2.3 is the smallest size; 3.5 matches nothing). Text now "2.3 to 4.7 times".
3. **Valence maximum.** From the saved exact histogram (64^3 and 32^3 give the same): valence maximum 0.463 eV, conduction minimum 1.243 eV. The "0.55 and 1.15" were not the edges: the Maxent density is below 1e-3 between 0.44 and 1.24 eV and below 1e-4 between 0.49 and 1.20 eV. Text corrected.
4. **SW ZPE 67.05.** Source: `bench_vdos.json` (M = 100, R = 2, matrix-free): 67.0505 (4096 atoms) and 67.0516 (32 768 atoms) meV/atom, relative difference 2e-5. Table V uses M = 170, R = 4 on the same SW-relaxed structure: KPM 66.573 vs exact 66.935. So the ZPE depends on M (0.48 meV, 0.7%, between M = 100 and 170) more than on the tiling. Text states both and the structure/M/R. This supports D4 (ZPE against M from exact moments).
5. **"20-60 Newton steps".** Wrong. `bench_accuracy_floor.json`: with s0 = 1e-4 the counts are 9, 11, 17, 22, 23, 24, 22 for M = 20 ... 400; the plain solver needs 9, 11, 34 and fails (299) from M = 100. Text now "9-24 steps"; Table III has two new columns with the Newton steps.
6. **Floor and sampled moments.** Checked the code (`maxent_fit`: sigma = max(sigma_sampled, floor); the exact moments n <= K have sigma = 0 so the floor acts on them; at R = 1 there is no variance estimate, so it is the whole regularization). Measured on DTW4096, R = 4, K = 0: sigma_n between 6.7e-4 and 4e-3 (median 3.6e-3) for n > 4, above the floor. Text: inactive for K = 0 and R >= 4; acts on the exact moments n <= K; essential for R = 1 (Table II).
7. **Graphene bootstrap.** The old numbers (9 s and 28 s "without convergence, same error") have **no log or script** in the repository and cannot be reproduced. New script `examples/fullerene/bootstrap_graphene.py` (Xu graphene, exact k-sum 240 x 240, exact moments, M = 400): bootstrap + floor 2.0 s, converged, L1 0.0444; plain + floor 3.8 s (31 steps), L1 0.0444; bootstrap without floor 29 s, converged, L1 0.0446; plain without floor 46 s, **not converged** (299 steps, residual 6e-8), L1 0.0449 (timings on 2 threads while other jobs ran, approximate). Text replaced by these numbers. [note] With the default floor the plain solver is already fast, so the bootstrap's advantage here is about 2x, not 3x.
8. **Superlinear stencil timing.** Right: the old 1902 s was not reproducible. Clean reruns (`examples/silicon/si_time.py`, M = 170, R = 4, K = 0, 4 threads, current tolerance, nothing else running): 32^3 cells 60.3 s (bounds 35.0 + moments 25.3), 48^3 (884 736 atoms) 264.4 s (169.5 + 94.9), 64^3 603.1 s (357.5 + 245.6, peak 1.8 GB); Maxent from the same moments adds < 1 s. Exponent 1.12 (moments 1.09, bounds 1.13). The old runs were made on 1 Nov while other jobs ran, which explains 1902 s. A second, genuine effect: the **bounds are not independent of N**: ARPACK needs 162, 222, 372, 392, 522 matvecs at 8^3, 16^3, 24^3, 32^3, 48^3 cells (`bounds_count.py`), so Sec. V (iii) ("independent of N") was wrong and is corrected. Abstract: "about 10 min" (was 32 min), "for explicit matrices exponent 1.01; for the matrix-free crystal 1.12". The "(with the earlier bound tolerance ...)" parenthetical is removed because the numbers it excused are gone.
9. **Headline timings are K = 0.** Abstract now says (M = 100, R = 2, no exact moments) and gives the default-settings time (380 s). Table VII has two new columns, moments and whole call at K = 4 (4096 ... 884 736 atoms: 1.2, 10.0, 36.6, 104.2, 201.0, 382.5 s). **Important finding behind this:** my first K = 4 run (legacy `exact.py`) was quadratic in N: moments 1.35, 26, 223, 1161 s at 16 384 ... 1.05 M orbitals (local exponents 1.4 to 1.9), so the paper's claim "the cost grows with K, not with N" was false for the code. Cause: the local method kept the columns P_m e_i as CSC blocks of n rows, so every sparse product converted an n-long index (O(n) per call, N/chunk calls). I **changed `src/sdos/exact.py`** to hold the columns as rows of a CSR block (the same arithmetic): the moments are identical (max difference 0 for K = 4, 2.8e-17 for K = 8 on DTW4096), 3x faster already at 131 072 orbitals, and linear thereafter (exponent 1.09; 342 s for the moments at 884 736 atoms instead of an extrapolated several hours). `pytest`: 183 passed, 1 skipped. The old function is kept in the scratchpad as `exact_legacy.py` and the legacy timings in `examples/bench/bench_kwon_k4_legacy.*`. **Please approve or revert the `exact.py` change.** Table I (16 384 orbitals, K = 4: 1.75 s vs 0.23 s) was measured with the legacy code; at that size the two versions differ by about 1.5x, so Table I is not re-measured here (not a correction of its efficiency ranking, which is dominated by the variance).

The first run's 10 GB cap was therefore too low by 4 GB. Table IX, Fig. 8, the exponent (Chebyshev, four sizes: 0.94) and the text are updated; four times that size would need 40-56 GB. The PCG row is still the recovered one (806 s, 9.8 GB); the build time (26 s) is from the rerun.
